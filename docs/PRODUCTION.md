# OverCard production runbook

How to move OverCard from the demo deployment to production without losing the current demo data, and how to operate it afterwards.

## 1. Before the first production deploy

| Item | Where | Notes |
|---|---|---|
| Paid web service (`starter`) | `render.yaml` | Always on. Live updates keep connections open, and the free tier sleeps after 15 minutes. |
| Paid Postgres (`basic-256mb` or larger) | `render.yaml` | Daily backups and no 90-day expiry. Audio is about 0.24 MB per recorded minute, so size the disk for it. |
| `JWT_SECRET` | Render → Environment | Generated by the blueprint. It must be 32+ characters, and the server refuses to start without it. |
| `CORS_ORIGIN` | Render → Environment | The frontend URL, for example `https://overcard.vercel.app`. |
| `APP_URL` | Render → Environment | The public app URL, used in owner recovery links. |
| `MASTER_CODE` | Render → Environment | A long random secret. Only people who have it can create organizations. |
| `DEMO_MODE` | Render → Environment | Leave it `on` until launch, then see section 5. |
| `UV_THREADPOOL_SIZE=8` | `render.yaml` | Keeps a burst of sign-ins fast. |

Syncing the blueprint changes billing. Upgrade the existing free database in place from the Render dashboard (Database → Settings → Instance type). That keeps the data and the connection string.

## 2. Moving the demo data to a new database

Use this only if the free database can't be upgraded in place, for example after it expired, or if you are moving providers.

```bash
# 1. Stop writes: suspend the web service (Render → overcard-api → Suspend)
# 2. Dump the old database (custom format keeps types, indexes and large audio rows)
pg_dump -Fc --no-owner --no-acl "$OLD_DATABASE_URL" -f overcard.dump
# 3. Restore into the new one
pg_restore --no-owner --no-acl -d "$NEW_DATABASE_URL" overcard.dump
# 4. Compare row counts on both sides
for t in orgs users teams decks sessions session_feedback session_shares session_audio notifications org_invites; do
  echo "$t old=$(psql "$OLD_DATABASE_URL" -Atc "select count(*) from $t") new=$(psql "$NEW_DATABASE_URL" -Atc "select count(*) from $t")"
done
# 5. Point DATABASE_URL at the new database and resume the service
```

## 3. Schema changes (migrations)

- **Boot sequence:** `initSchema()` runs on every boot. It first creates the baseline schema with idempotent `CREATE`/`ALTER … IF NOT EXISTS`. It then applies the numbered files in `server/migrations/` that aren't yet recorded in the `migrations` table.
- **Locking and transactions:** migrations hold an advisory lock, so two instances can't run them at once. Each migration runs in its own transaction; a failure rolls that file back and stops the boot with the error.
- **Adding a change:** create `NNN_name.js` exporting `{ name, up(client) }` and list it in `server/migrations/index.js`. Never edit or reorder a migration that has shipped.
- **Re-running is safe:** a second boot applies nothing.
- **Migration `006_integrity` requires unique emails ignoring case.** If two accounts differ only by capitalisation, the boot stops and lists them. Merge or rename one, then redeploy.

## 4. Backups and restores

- **Automatic:** Render paid Postgres takes daily backups, with point-in-time recovery on larger plans. Restore from Render → Database → Recovery.
- **Manual snapshot:** take one before risky changes with `pg_dump -Fc "$DATABASE_URL" -f overcard-$(date +%F).dump`. Store it somewhere other than the Render account.
- **Restore drills:** test a restore into a scratch database every quarter, using `pg_restore` as in section 2.

## 5. Turning demo mode off at launch

1. Create the real organization or organizations: the sign-up screen, then "Create organization" with `MASTER_CODE`.
2. Set `DEMO_MODE=off` and redeploy. The demo orgs stop being re-seeded, the one-click demo picker disappears, and demo sign-in is disabled. **Nothing is deleted**, and real orgs never see demo data, because every query is scoped to the signed-in user's org.
3. The demo accounts still exist with the demo password. To remove them later, delete the two demo orgs' users from each org's Admin panel, or ask for a cleanup script.

## 6. Account recovery

| Who | How |
|---|---|
| A user or admin | An admin or the owner opens Admin → People → the person → Reset password, then sends them the one-time link (1 hour, single use). Only the owner can reset an admin. |
| Anyone signed in | Profile → Change password. The current password is required, and other sessions are signed out. |
| The owner | Run `npm run owner-reset -- owner@company.com` from Render → Shell. It prints a one-time link valid for 1 hour. Set `APP_URL` so the link is complete. |

Email-based "forgot password" is not built yet. The `password_resets` table and `/auth/reset` endpoints are ready for it: an email step only needs to create the same token and send the link.

## 7. Security model (summary)

- **Passwords:** bcrypt at cost 12. Reset tokens are stored only as SHA-256 hashes, are single use and last 1 hour.
- **Sessions:** a JWT (HS256) in an HttpOnly cookie. The server stores only a SHA-256 hash of the active session id, and one device can be signed in at a time. Signing in elsewhere, a password change or reset, or account removal signs the old device out instantly over the live stream. A run it had in progress is saved as abandoned.
- **Token in the browser:** stored only when the API is on a different site from the app (the Safari third-party-cookie fallback). On a same-origin deployment the token is never written to browser storage.
- **Tenant isolation:**
  - Every query is scoped by the caller's org, taken from the database rather than from the token.
  - Live events go only to channels the server derives from the signed-in user.
  - `npm test` (`tests/isolation.test.js`) probes every endpoint across orgs.
- **Data at rest:** Render Postgres encrypts disks at rest. Recordings, emails and phone numbers are not additionally column-encrypted.
- **Rate limits:**
  - Sign-in: 10 per 15 minutes.
  - Signup: 10 per 15 minutes.
  - Invite preview: 30 per 15 minutes.
  - Reset links: 20 per 15 minutes.
  - Password change: 10 per 15 minutes per account.
  - Whole API: 600 per minute per account.
- **Logs:** production errors log the message, code and route only, never full database rows.

## 8. Same-origin API (recommended hardening)

Serving the API under the app's own domain makes the session cookie first-party, so no token ever needs browser storage. With Vercel, add this rewrite to `vercel.json` before the SPA rewrite:

```json
{ "source": "/api/(.*)", "destination": "https://<your-render-service>.onrender.com/api/$1" }
```

Then build without `VITE_API_URL` and remove `CORS_ORIGIN`. Before relying on it, check that the live stream (`/api/events`) stays connected through the proxy for several minutes. If the proxy cuts long connections, the app reconnects automatically, but often.

## 9. Capacity

`npm run loadtest` simulates 100 people working at once: live sessions with heartbeats, browsing, feedback, sharing and deck edits, while admins watch the live monitor. It reports latency per endpoint and live-event delay. Run it against a staging copy, never against production data. A single `starter` instance handles 100 concurrent users. Live updates use one in-process event bus, so running more than one instance would first need that bus moved to Postgres `LISTEN/NOTIFY`.
